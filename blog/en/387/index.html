🤔 Evaluation metrics: getting STLC into AppSec correctly

Salute.

I often show a slide with eight evaluation metrics from STLC - this is a classic of the QA world. At the conference, which was held, I caught an insider: the need to convey the suitability for AppSec, when we equate bugs with vulnerabilities in the code base. Therefore, I will share my thoughts with you. In general, these metrics are needed, but not directly, because they cannot be copied, they need to be redefined.

First, let’s agree with you this way - the main substitution is buried here, where in STLC a defect is a bug, a test is a test case, a requirement is a functional requirement. Now the funny thing is:

• A defect is a confirmed True Positive vulnerability

• Test - rule/analyzer policy ruleset

• Requirement - threat class CWE, ASVS control, safe development clause GOST 56939-2024

Now check out the slide:

• Rule strength = confirmed vulnerabilities (TP) / number of active ruleset rules

- Low on ruleset, where the rules are broken or dead

— Abnormally high on one rule, there is either a system defect in the code, or the rule is faulty

• Percentage of threat class coverage (breadth) = CWE classes and controls actually checked by the toolchain / all relevant to the stack × 100%

— <60% — toxic

— 60–85% — working area

— > 85% — mature coating

• Proportion of rejected positives = (FP + accepted / risk accept) / all positives × 100%

— high due to FP, then the tool fails, therefore we audit the rules

— high due to accepted risk, that is, that the process is crashing, escalate

• Coverage density (depth) = number of rules / number of controls (CWE / ASVS)

— < 1, shows that the control is formally covered

— several rules with different logic (AST + taint analysis + semantic ruleset)

• Vulnerability density = confirmed vulnerabilities (TP) / codebase coverage (Secure Code Review candidates)

• Share of regressions of vulnerabilities (reopen rate) = vulnerabilities that returned after “elimination” / all eliminated × 100%

- > 15% - they fix the wrong thing and the wrong place

— for each eliminated Critical/High, a rule is followed in the Quality Gate

• AppSec efficiency = vulnerabilities weighted by criticality / AppSec effort (hours scan + triage). The weights are usually: Critical 10, High 5, Medium 2, Low 0.5, and it’s better to turn it into “the cost of one Critical find” = hours / Critical number.

• Density of vulnerabilities after delivery = vulnerabilities found in PROD / volume of code base (about the result). If the density does not drop from release to release, we go into the team’s project management and collect evidence for them. Consider Defect Removal Efficiency for information security = found before release / (before release + after) × 100%.

Total:

• The breadth of coverage and depth (density of rules) should be considered in pairs - once a sprint in detail according to critical CWE, a general summary once a quarter or H

• The share of rejected ones is always split into FP and accepted risk

• Density of vulnerabilities and share of regressions see each release

• Efficiency is calculated through the cost of Critical-finds

• The main maturity KPI is Defect Removal Efficiency for information security > 90%
