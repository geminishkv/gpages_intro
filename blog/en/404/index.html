🛠 Error codes and information leakage via HTTP methods

Salute, I’m actually torn, there will be some cool news soon, we’ll see how it goes and what happens.

Today I want to talk to you about the topic of HTTP methods, so let’s start with the fact that DAST is not only a search for XSS and injections, but specifically when the application itself gives away confidential information in responses to crooked or non-standard requests.

Example: GET with redundant information, POST without a body, TRACE - and the server begins to tell more about itself than it should

What is leaking and where from?

• Error codes - 500 Internal Server Error with stack trace in the body of the response is the name of the framework, version, path to files, sometimes the connection string to the database. Let’s say 403 Forbidden differs from 404 Not Found, where we can search for closed endpoints. And 405 Method Not Allowed directly says that the endpoint exists

• Verbose errors in the body - for example, ASP.NET in development mode gives a full stack trace in HTML. And Spring Boot without server.error.include-stacktrace=never does the same thing in JSON. Besides, Django with DEBUG=True is a different story and very hemorrhoidal

• Response headers - Server: Microsoft-IIS/10.0, X-Powered-By: ASP.NET, X-AspNet-Version: 4.0.30319 give us an understanding of the stack, runtime version and the platform itself, that is, the very first thing before the exploit

• TRACE method - reflects the request back in its entirety, including headers, where you can see the internal headers that are added by the reverse proxy or balancer, sometimes tokens (here I looked in more detail)

Let's poke curl

# GET with a non-existent path - see what errors are in the body

curl -i https://example.com/api/v1/doesnotexist123

# POST without body and Content-Type - trigger a parsing error

curl -i -X POST https://example.com/api/v1/orders

# POST with curved JSON - often pulls out stack trace

curl -i -X POST https://example.com/api/v1/orders\

-H "Content-Type: application/json" \

-d '{"broken json'

# TRACE - check whether the method is enabled

curl -i -X TRACE https://example.com

# We look only at the headers - we look for Server, X-Powered-By, X-AspNet-Version

curl -s -D - https://example.com -o /dev/null | grep -iE\

"server:|x-powered|x-aspnet|x-generator|x-runtime"

What do we see?

# verbose error with stack details

HTTP/1.1 500 Internal Server Error

X-Powered-By: ASP.NET

{

"message": "Object reference not set to an instance of an object",

"stackTrace": "at ProjectQueryRepository.GetById(Int32 id)\r\n

at C:\\inetpub\\b2b\\src\\Repositories\\ProjectQueryRepository.cs:75"

}

# TRACE reflects the request back

HTTP/1.1 200 OK

TRACE /api/test HTTP/1.1

Host: example.com

Authorization: Bearer eyJhbGc... ← token in reflection

# But there’s nothing superfluous here

HTTP/1.1 500 Internal Server Error

{ "error": "Internal server error", "requestId": "a3f9c2" }

Total

• 500 with error body - the first thing DAST checks

• The difference between 403 and 404 on closed endpoints is enumeration, non-existent and inaccessible should be indistinguishable from the outside

• Server: and X-Powered-By: remove at the nginx/IIS level - they are not needed by the client

• The only thing we give in case of an error is requestId, everything else is hidden in internal logs

• Bursts of 500 and non-standard methods - detectable active search pattern

• Consistency of response codes - a non-existent resource and a resource that cannot be accessed should be indistinguishable from the outside - both return 404

• Server:, X-Powered-By:, X-AspNet-Version:, X-AspNetMvc-Version:, X-Generator:, X-Runtime: remove at the web server or reverse proxy level, since it does not provide any value for business functions

• Make a Whitelist of allowed methods: GET, HEAD, POST, PUT, DELETE, PATCH depending on the API, TRACE itself is disabled everywhere

• Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options and other security headers are a separate layer that closes exploitation even if some information is leaked. Without them, a leak of a framework version in conjunction with a known CVE and the absence of a CSP turns into a chain in one step
