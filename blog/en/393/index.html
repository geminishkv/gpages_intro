🤔 S.T.R.I.D.E. as a working solution for modeling and controlling information security threats

Fireworks,

Let's take a look today at the six classes of threats described in S.T.R.I.D.E. In fact, this could be seen in many speeches, but it is better to explain the meaning and principle, since without the harness it does not work and to turn it into a tool you need DFD and binding to mitigation controls.

We don’t live in a perfectly illusory world and we always have to “pull” something somewhere.

The foundation is a Data Flow Diagram, like threat modeling with data flows and trust boundaries. In fact, you will have these: external entity, processes, flow, data store, trust boundaries. After only this you can move on to S.T.R.I.D.E. itself. Conceptually, this is all analytics according to the principle:

• Which property of the Parker hexad is violated?

• Typical vectors

• Controls

• Mitigation and information security risk assessment

S.T.R.I.D.E.

• S - Spoofing: substitution where the authenticity of the subject is violated

Vectors:

• user substitution, session fixation, token replay

• service spoofing, such as MITM, fake endpoint, DNS hijack, lack of mTLS between microservices

• replacing identity in logs via X-Forwarded-User without checking

Controls: MFA, mTLS with certificate verification, OAuth2/ OIDC with PKCE, token binding, DPoP type, mTLS-bound, WebAuthn/ FIDO2, anti-replay (nonce, timestamps, jti)

• T - Tampering: falsification where integrity is violated (data flow (in transit), data store (at rest), process (integrity of code and configs))

Vectors:

• traffic modification

• substitution of request parameters (IDOR via hidden fields, JWT with alg=none, client-side state manipulations)

• modification of stored data bypassing the application

• supply chain: replacement of assembly artifacts, images, dependencies

Controls: TLS current versions, digital signatures and HMAC, integrity control (checksums, FIM), append-only / WORM logs, signed commits, signed images, SBOM, configuration control)

• R - Repudiation (refusal to act), where non-repudiation and accountability are violated

Vectors:

• the user denies the action, but there is nothing to prove

• shared/service accounts without identification

• the admin modifies the logs after the fact

• the developer commits without a signature to the shared branch

Controls: centralized logging with integrity protection (append-only, WORM), NTP time synchronization, correlation in SIEM, digital signature of sensitive operations, signed commits, prohibition of shared accounts

• I - Information Disclosure (disclosure of information), where confidentiality is violated

Vectors:

• unencrypted transmission

• stack trace and detailed errors in the response to the user

• BOLA / IDOR - accessing foreign objects by searching for ID

• PII (personification) and secrets in logs

• side-channel: timing, response size, cache differences

Controls: TLS, at-rest encryption (envelope / KMS / HSM), generic error responses without details, output filtering and explicit DTOs, PII masking in logs, data minimization, secret management

• D - Denial of Service, where availability is disrupted

Vectors:

• volumetric DDoS levels L3/L4

• application-layer DoS: slow requests (slowloris), catastrophic regex backtracking, zip/XML bombs, billion laughs

• resource exhaustion: memory leaks, connection pool, unbounded queues

Controls: rate limiting and throttling, WAF / DDoS protection, size, time and depth limitations, circuit breakers, auto-scaling, backups and DR, capacity planning

• E - Elevation of Privilege, where: authorization is violated

Vectors:

• BOLA / BFLA: no check of permissions on an object or function

• vertical escalation

• horizontal escalation

• sandbox escape

• JWT-tampering

• RCE via deserialization

Controls: RBAC / ABAC with deny-by-default, authorization check on each request (and not just once at the entrance to the API gateway), Segregation of Duties, least privilege, container isolation (rootless, seccomp, AppArmor / SELinux), login validation, role-claims from the client
