🛠 Terrascan IaC policy for configurations

The tool analyzes Infrastructure as Code (IaC) patterns and checks them against built-in security policies. Scans HCL, YAML and JSON configs for errors, architectural deficiencies, violations of practices and compliance issues.

Basic mapping to CIS Benchmarks, NIST, SOC2, GDPR, HIPAA out of the box.

Metadata: Apache 2.0. Report formats: CLI, JSON, YAML, XML, JUnit-xml, SARIF. Supports Terraform, Kubernetes, Helm, Dockerfile, CloudFormation, etc. Contains predefined policies for providers: AWS, Azure, GCP, Kubernetes and Docker. Policies are written in Rego (Open Policy Agent), which allows you to create your own rules.

# Scan the current directory with auto-detection of IaC type

terrascan scan

# Scan indicating IaC type and cloud provider

terrascan scan -i terraform -t aws

# Output results in JSON format

terrascan scan -o json

# Filter by severity

terrascan scan --severity "High"

#Dockerfile

terrascan scan -i docker

# Display vulnerabilities in images mentioned in IaC files

terrascan scan -i terraform --find-vuln

Custom policy for images without an explicit version tag

# policy/no_latest_tag.rego

package accurics.docker.image.latest

deny[msg] {

input.type == "dockerfile"

instruction := input.instructions[_]

instruction.cmd == "from"

contains(instruction.value, ":latest")

msg := sprintf("Image uses ':latest' tag: %v", [instruction.value])

}

CI/CD integration

terrascan:

image: tenable/terrascan:latest

stage: security

script:

- terrascan scan -t terraform -d ./infra -o sarif > terrascan.sarif

- terrascan scan -t docker -f Dockerfile -o json > docker.json

artifacts:

reports:

sast: terrascan.sarif

allow_failure: false # block the pipeline at HIGH/CRITICAL

pre-commit hook

# .git/hooks/pre-commit

#!/bin/bash

terrascan scan -t terraform -d . --severity HIGH --exit-code 1

if [$? -ne 0 ]; then

echo "BLOCKED: Terrascan found HIGH/CRITICAL violations"

exit 1

fi

Total:

• Unified IaC for Terraform, Kubernetes and Helm out of the box

• Ability to write custom rules in Rego for internal requirements

• The tool analyzes code before it is deployed and does not monitor runtime threats in the running infrastructure. Parameterized resources are checked by the value that is visible in the config

• More suitable for Kubernetes clusters and related technologies

• You can specify which rules to ignore (--skip-rules)

• Allows you to customize QG criteria based on their severity
