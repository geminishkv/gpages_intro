SEC-3 Dependency Chain Abuse

The build system automatically resolves and executes third-party code when installing dependencies: npm install or pip install. Three vectors:

• Dependency confusion. The internal package myorg-utils lives in a private registry. The attacker publishes a package with the same name in public npm/PyPI, but with a higher version. The resolver by default pulls the latest one, and the internal name leaks easily: into package.json

• Typosquatting. Reqiests instead of requests, python-dateutils instead of python-dateutil. There is a typo in the name and the attacker's package with an install hook is installed

• The maintainer deleted the account, the email domain expired, abandoned the project - the attacker re-registers and rolls out the malicious version under a trusted name

Case

February 2021, Alex Birsan: using one dependency confusion technique, I entered the assemblies of Apple, Microsoft, PayPal, Shopify, Tesla, Uber, publishing packages in public npm/ PyPI/ RubyGems with the names of their internal libraries and a higher version - the assemblies themselves pulled them up. More than $130k in total in the bounty, and it was not a hole in the code, but the logic of resolving packages

Total

• Scopes/ namespace for internal packages (@myorg/...) with a strict link to the private registry

• Lock and crypto hashes: pip install --require-hashes, npm ci by package-lock.json

• Private proxy (Nexus/ Artifactory): a single point where internal names are not resolved outside

• Namespace protection: take your names in advance as defensive registration - SCA for each PR OSV-Scanner, Trivy

How does it work?

# .npmrc - internal scope only for private registry

@myorg:registry=https://nexus.internal/repository/npm-private/

# everything else is done via proxy, without direct access to npmjs

registry=https://nexus.internal/repository/npm-proxy/
