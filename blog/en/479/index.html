🛠 Bearer is like a data-centric SAST, not code-centric

Salute, look, today let's take a look at the cool SAST, which can be used in PDn.

The functionality in the style is not “SQL injection on line 42”, but: “SQL injection on line 42, which processes user.email and user.phone, and the result goes to the external API on line 87.”

A cool variation of working with sensitive data flow tracking? I think so. That is, the tool determines where PD gets into the application - user input, API, database, as well as how it moves through functions and where it ends up in the end - in logs, in an external service, in an API response. In this case, finds are ranked according to the presence of sensitive data in the chain.

Out of the box - 473 rules, OWASP Top 10 and CWE Top 25. Plus privacy scanner: automatically generates a report on where and how personal data is processed - straight to the topic for those who work with 152-FZ and RKN. CLI open source for ELv2.

Teams

# Basic scan of current repo

bearer scan.

# Only critical and high

bearer scan. --severity critical,high

# Privacy report on how PD moves and where it goes

bearer scan. --report privacy

# Data flow map - a complete picture of data movement

bearer scan. --report dataflow

CI/CD integration

# GitHubActions

- uses: bearer/bearer-action@v2

with:

severity: critical,high

format: sarif

# GitLab CI

bearer:

image: bearer/bearer:latest

stage: security

script:

- bearer scan. --format sarif --severity critical,high > bearer.sarif

artifacts:

reports:

sast: bearer.sarif

allow_failure: false

Custom rule: PD in logs

# rules/no_pii_in_logger.yml

languages:

- python

metadata:

id: custom_no_pii_in_logger

description: "The user's personal data is included in the logger"

severity: high

patterns:

- pattern: |

logger.$method($user.$pii)

Typical finds

# Email leak to the log - Bearer will catch it, but Semgrep may miss it

logger.info(f"Processing payment for {user.email}")

# PD goes to external API without masking

requests.post(external_url, json={"phone": user.phone, "amount": amount})

# Passport data in the request parameters (GET = see proxy logs)

redirect(f"/verify?passport={user.passport_number}")

Total

• Not just “a vulnerability found”, but “the vulnerability and chain of movement of PD, as well as where it leaks”

• Privacy report out of the box - for teams working with 152-FZ, this is a ready-made artifact for compliance

• Weak point: cross-file analysis only in Pro (Cycode)

• Paired with Semgrep, it covers different niches: Semgrep - business logic and custom patterns, Bearer - data privacy and personal data flows
