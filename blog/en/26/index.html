🛠 .gitignore: why is ignoring redundant artifacts important?

Firework,

It often happens that the development team in its projects does not exclude artifacts that do not participate in assemblies, but are stored in GitSCM project branches, and with a change history.

Let's take a closer look:

.gitignore is an ignore config (actually a file) for Git, which tells it which files and directories should be ignored, that is, not tracked and not added to the repository.

Most often used to ignore temporary or test or build files, as well as other elements that are not needed in the project history. Therefore, there are extensive descriptions of ignores in product reports that indicate only exceptions that are undesirable for the development cycle. For example:

1. Files generated during and as a result of project compilation. Typically, they have directories with names like target/, output/, release/, debug/

2. Files generated by a test framework, profiler, debugger, etc.

3. Documentation generated from code - only if it is not generated into a separate repository, through which a website with documentation is then deployed (example gpages)

4. Files created when the code is executed: logs (*.log), work results, etc.

5. Temporary files of a text editor or development environment (*~)

6. Files created by the operating system, for example thumbs.db, .DS_Store

Example:

- The output is stored in C# so that you can easily build the project, but you can configure what runs when building, but this is not possible for all scripts

- To store or not to store composer.lock - you need to understand how it works

- You can’t ignore .idea/, because the project settings will fall off, or you can’t just take and leave .idea/, because personal paths will get to everyone and create conflicts.

Remark:

For storage, there is a cool option, such as using packages in the form of an artifact (we will consider it later). If you can use NuGet, Composer, CPAN, Lein, Maven, then the binary dependencies should be there.

In summary: I recommend excluding not only what is not used, but also what may contain some history of important changes that will allow the project to be re-searched.
