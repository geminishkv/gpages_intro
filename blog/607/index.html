🏆 Свой образ cdxgen в условиях ограничений: зачем и как?

Салют,

Давай сегодня посмотрим на задачку, когда готовый cdxgen-python312 не прошёл внутренний гейт, потому что его база SLES 15.6 несёт 4 Critical и 130 High на любой версии. Но как-то странно, не?

12.6.0 тащит tar с Critical, и overrides тут не спасают, так как гейт смотрит опубликованный пакет, а не итоговое дерево.

Взяли 12.8.3 с чистым собственным lock, а undici 7.28.0 (High CVE-2026-13697) подняли через overrides до 7.30.1 — уже для чистоты своего образа и просто для кайфа

Это уязвимости базы, а не cdxgen, но гейту это безразлично и поэтому приходится решать не стандарный кейс. Есть конечно еще временный вариант под Java 11, но ставил проект через pip внутри образа, то есть исполнял чужой сборочный код - что тоже не самое корректное

Что пришлось собрать и сделать безопасным?

• Многоэтапная сборка:

— node:24-alpine

— npm игнорирование --omit=dev, --ignore-scripts

— lock-файл с хешами, также все базы по digest (версия cdxgen берётся из package.json, в конфиг шага CI уходит адрес образа по digest)

• Вшита учётку реестра и корень внутреннего УЦ, которая приходят секретами сборки и в слоях их нет

• База distroless/nodejs24-debian13:nonroot без shell и пакетного менеджера

• Стоит USER 65532, а HEALTHCHECK NONE так как одноразовый CLI

— uv и Python 3.12 (stdlib без pip, ensurepip, idle и tkinter) только для резолва проектов без lock-файла

— при сборке: hadolint, Checkov, trivy config, SBOM образа, trivy image

— Публикация в registry только при нуле Critical и High сработок

Как запускаем?

• Каждый каталог проекта — это отдельный запуск с --no-recurse (рекурсивный проход брал uv.lock и терял requirements.txt соседнего каталога)

• Каталог монтируется только на чтение, SBOM забирается docker cp, а на агентах docker rootless

• Есть lock-файл: --network none, --no-install-deps

• Нет lock-файла:

— uv pip compile --no-build --no-config --no-python-downloads по внутреннему индексу, то есть ничего не ставится и не собирается, код проекта и зависимостей не исполняется

— --no-config не даёт проекту подменить индекс через uv.toml

• cdxgen строит SBOM по полученному requirements.txt уже без сети

• Учётка индекса попадает в контейнер только по имени переменной окружения

• Вход в реестр — во временный DOCKER_CONFIG, который удаляется

• Dev-зависимости режет отдельный фильтр по разметке lock-файлов (npm, yarn, pnpm, uv, poetry, pdm, Pipfile, composer)

• Для Frontend зависимости бандла часто лежат в devDependencies и едут в прод

Как контролируем?

• Образ пересобирается при новой версии cdxgen и обновлении баз отдельной джобой с теми же проверками

• Trivy не видит интерпретатор Python в /usr/local: пакетных метаданных у него нет (обновление путем смены digest базы)

• Пакет без колёс или проект с динамическими метаданными через --no-build не проходит: шаг падает громко, с именем пакета, а не отдаёт пустой SBOM

Troubleshoot

• BuildKit при --network host пишет свой /etc/hosts: имя внутреннего реестра уходит во внешний DNS и лечится --add-host

• В сетях контейнеров на агентах нет DNS: резолв идёт с --network host, режим lock-файла — с --network none

• netrc под rootless не читается, uv молча идёт без учётки

Итог

• Для тебя готовый образ может оказаться не подходящим длявнутреннего контура, потому что база не проходила гейт, а режим без lock-файла исполнял код проекта

• При этом свой образ на distroless закрыл обе проблемы: без shell, от nonroot, по digest, ноль Critical и High уязвимостей - а логика и функционал не потеряны, только ограничены тем, что у тебя используется в контуре

• SBOM строится по каждому каталогу: с lock-файлом без сети, без lock-файла — через uv без сборки

• Боль — поддержка образа и пара записанных слепых пятен (лучше чем безусловное принятие рисков ИБ)
